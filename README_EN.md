# Chestnut-Pi-YOLOv8-demo — Full YOLOv8n toolchain (pt → ONNX → OM)

[简体中文](README.md) | **English**

A `yolov8_demo` environment built from scratch inside **WSL2 (Ubuntu 22.04 x86_64)**,
with every dependency required by the full `yolov8n.pt → yolov8n.onnx → yolov8n_bs1.om`
toolchain installed — and **the whole pipeline has actually been run end to end**.

Target hardware: **Chestnut Pi Ascend 310B** (Atlas 200I DK A2, `soc_version=Ascend310B1`).

### 2.1 What each stage needs

| Stage | Dependencies | Requirement |
|---|---|---|
| pt → onnx | `torch` + `ultralytics` + `onnx` + `onnxslim` | Done inside WSL2 |
| ONNX verification | `onnxruntime` | Done inside WSL2 |
| **onnx → om** | **CANN Toolkit's `atc`** + TBE's Python deps | Done inside WSL2 (**no NPU, no driver needed**) |
| OM inference | Board-side pyACL (ships with the board's CANN) + `/dev/davinci*` | **Must run on the development board** |

> **Key point**: ATC is a **compiler**. It turns ONNX into a 310B OM on an ordinary
> x86 PC — no NPU has to be attached. But an OM only loads on the **same chip model**,
> so the inference step has to move to the board (`scripts/infer_om.py` here).

### 2.2 Two hidden dependencies that will block you

1. **`libascend_hal.so`**: `atc.bin` links against this library dynamically, and it is
   normally provided by the **NPU driver package**. Without a driver installed you get:

   `error while loading shared libraries: libascend_hal.so`

   The CANN Toolkit **ships a stub version**, so just add it to the library search path:

   ```bash
   export LD_LIBRARY_PATH="${LD_LIBRARY_PATH}:/usr/local/Ascend/ascend-toolkit/latest/runtime/lib64/stub"
   ```

   > ⚠️ **The stub directory must be appended LAST, never prepended.**
   > `runtime/lib64/stub/` contains a set of **same-named** hollow libraries
   > (`libascendcl.so`, `libacl_dvpp.so`, ... — only a few dozen KB, with no
   > implementation symbols). If the stub path comes first, those hollow libraries
   > win the lookup and **pyACL import fails**:
   > `ImportError: .../acl.so: undefined symbol: aclprofSetConfig`
   >
   > What makes this error so nasty: `atc` only needs `libascend_hal.so` from the stub,
   > so it works with either ordering — **the problem only surfaces when you run
   > inference through pyACL**.

   `scripts/atc_convert.py` and `atc_convert.sh` detect this automatically and set it up
   (they inject the path into the `atc` child process only, leaving your shell untouched).

2. **ATC's TBE uses the system `python3`, not the conda interpreter.**
   Even when `numpy` is already 1.26.4 after `conda activate yolov8_demo`, ATC can still
   fail with `np.float_ was removed` — because it runs `/usr/bin/python3`. You must install
   `numpy<2` and the TBE dependencies for the system python3 as well (see 3.1, step 6).

### 3.0 About "requirements.txt just won't install"

Writing `pip install requirements.txt` (without `-r`), or putting several packages on one
line, makes pip fail immediately. The four traps and their fixes:

| Trap | Error | Fix |
|---|---|---|
| Missing `-r` | `Could not find a version that satisfies the requirement requirements.txt` | `pip install -r requirements.txt` |
| Multiple packages per line | `Invalid requirement: 'torch==2.5.1+cpu  torchvision==...': Expected comma...` | One package per line |
| `torch==2.5.1+cpu` | `No matching distribution found for torch==2.5.1+cpu` | Add `--extra-index-url https://download.pytorch.org/whl/cpu` |
| `ml_dtypes==0.6.0` + `numpy==1.26.4` | `ResolutionImpossible` (0.6.0 requires numpy>=2) | Relax it to `ml_dtypes<0.6` |

`env/install_requirements.sh` handles all four automatically — you can even hand it the
**original multi-package-per-line file** and it will normalise it first (verified: 17 lines
holding 57 packages, installed from scratch to fully working).

## 4. Running the full toolchain

```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh    # required in every new terminal
conda activate yolov8_demo
cd /path/to/Chestnut-Pi-YOLOv8-demo

python scripts/run_all.py                             # runs all 5 steps
```

You can also run the steps individually, which makes debugging easier:

```bash
# [Layer 1] PyTorch baseline — every later accuracy number is compared against it
python scripts/pt_baseline.py --image data/images/bus.jpg

# [Layer 2] pt -> onnx (opset 11, static shapes)
python scripts/export_onnx.py --pt model/yolov8n.pt --onnx model/yolov8n.onnx

# [Layer 2] ONNX self-check (structure + ONNX Runtime numerics)
python scripts/check_onnx.py --onnx model/yolov8n.onnx --image data/images/bus.jpg

# [Layer 3] onnx -> om (the slowest step, roughly 5–10 minutes)
python scripts/atc_convert.py --onnx model/yolov8n.onnx --out model/yolov8n_bs1

# [Board] OM inference (run this on the development board)
python3 scripts/infer_om.py --model model/yolov8n_bs1.om --image data/images/bus.jpg
```

### 4.1 The equivalent raw ATC command

`scripts/atc_convert.py` assembles exactly this command:

```bash
atc --model=model/yolov8n.onnx \
    --framework=5 \
    --output=model/yolov8n_bs1 \
    --input_format=NCHW \
    --input_shape="images:1,3,640,640" \
    --soc_version=Ascend310B1 \
    --log=error
```

| Option | Value | Notes |
|---|---|---|
| `--framework` | 5 | 5 = ONNX, must be correct |
| `--output` | model/yolov8n_bs1 | Output prefix; ATC appends `.om` |
| `--input_format` | NCHW | Always NCHW for image models |
| `--input_shape` | images:1,3,640,640 | The node name **must** match the ONNX graph, otherwise you get E10016 |
| `--soc_version` | Ascend310B1 | Chip model of the Chestnut Pi 310B |
| `--log` | error | Errors only |

A pure shell equivalent is provided too: `bash scripts/atc_convert.sh` (parameters such as
`SOC_VERSION` / `INPUT_SHAPE` can be overridden through environment variables, which makes it
easy to call from CI).

## 4.2 OM inference only runs on the board

`scripts/infer_om.py` uses the board-side pyACL and needs the `/dev/davinci0` device node,
so it **must be executed on the development board**. Copy the project directory to the board
(or share it over NFS/SSH) and run:

```bash
# on the development board
source /usr/local/Ascend/ascend-toolkit/set_env.sh
python3 scripts/infer_om.py --model model/yolov8n_bs1.om --image data/images/bus.jpg
```

The script prints model information (input/output shapes, dtypes, byte sizes) and the
detections, and writes the visualization to `results/om_result.jpg` plus the raw output to
`logs/om_raw_output.npy` (feed it to `check_om_out.py` with `--npy logs/om_raw_output.npy`
to confirm the layout).

> The board's CANN version must be **compatible** with the one used for conversion. This repo
> converts with CANN 8.0.RC1; if your board runs CANN 7.0.RC1, re-convert on the board with
> that version's ATC (the parameters are identical).

## 5. Pitfalls we hit (indexed by error message)

| Error / symptom | Cause | Fix |
|---|---|---|
| `CondaToSNonInteractiveError` | conda 26+ requires accepting the Anaconda channel ToS first | `conda tos accept --override-channels --channel https://repo.anaconda.com/pkgs/main` (both channels) |
| `conda env list` shows no env, yet pip installed into base | `conda create` failed but the script did not check the exit code, so `conda activate` silently failed | Use the **absolute path** `$CONDA_ROOT/envs/<env>/bin/python -m pip` instead of relying on activate |
| **`atc.bin: error while loading shared libraries: libascend_hal.so`** | No NPU driver installed; that library normally comes with the driver package | The toolkit ships a stub — **append** it to the end of the library path: `export LD_LIBRARY_PATH="${LD_LIBRARY_PATH}:.../runtime/lib64/stub"` (the scripts do this automatically) |
| **`ImportError: acl.so: undefined symbol: aclprofSetConfig`** | The stub path was placed **first** in `LD_LIBRARY_PATH`, so the hollow `libascendcl.so` was loaded | Move the stub to the **end**: `export LD_LIBRARY_PATH="${LD_LIBRARY_PATH}:.../runtime/lib64/stub"`. Note `atc` works with either ordering — only pyACL exposes this |
| **CANN installer hangs forever after `--install --quiet`** | It forks an `xfce4-terminal` to show a progress bar, and that process never exits | `pkill -f 'Ascend-cann-toolkit'; pkill -f 'xfce4-terminal -e'`, then confirm `/usr/local/Ascend/ascend-toolkit/latest/bin/atc` exists |
| atc reports `host_env_os 参数无效` (invalid host_env_os) | `set_env.sh` was not sourced; ATC infers the host platform from environment variables | `source /usr/local/Ascend/ascend-toolkit/set_env.sh` |
| **`EC0010: ... [AttributeError: np.float_ was removed ...]`** (still happens with numpy 1.26.4 in conda) | **ATC's TBE uses the system `python3`, not the conda interpreter** | Install numpy<2 for the system python3 too: `pip install --target=/usr/local/lib/python3.10/dist-packages numpy==1.26.4 ...` (README 3.1 step 6) |
| `EC0010: Failed to import Python module [No module named 'scipy']` | TBE's Python dependencies are missing | `pip install decorator attrs psutil scipy synr absl-py tornado` |
| `E10016: Opname [input] ... is not found` | The `--input_shape` node name does not match the ONNX graph | For YOLOv8 it is `images`; confirm with `check_onnx.py` |
| `E10054: [--soc_version] is empty` | `--soc_version` omitted | Add `--soc_version=Ascend310B1` |
| `module 'cv2' has no attribute 'setNumThreads'`, ultralytics import fails | `opencv-python` and `opencv-python-headless` are installed together and overwrite each other | Uninstall `opencv-python`, keep only `opencv-python-headless` |
| ultralytics export prints `simplifier failure: No module named 'onnxslim'` | ultralytics 8.3.x prefers onnxslim (not onnxsim) and installs it at runtime, too late for the current run | `pip install onnxslim` and re-run; or ignore it (conversion works without simplification) |
| ATC hangs / load spikes | `--precision_mode=force_fp32` makes ATC hang | **Do not pass that flag** |
| Specifying FP16 makes it slower | The 310B AI Core computes in FP16 anyway; forcing FP16 inputs inserts extra conversion ops | Use the defaults (no `--input_fp16_nodes`) |
| `Import acl` fails | CANN environment variables were not sourced on the board | On the board: `source /usr/local/Ascend/ascend-toolkit/set_env.sh` |
| `RuntimeError: 输入字节数不匹配` (input byte count mismatch) | ATC's `--input_shape` disagrees with the pre-processing output shape | Both must be `(1,3,640,640)` |

## 6. Layered verification strategy

Each of the three layers is independently verifiable, which is the key to debugging —
**if a layer fails, there is no point continuing downward**:

```
[Layer 1] PyTorch   produces boxes  ──→  the accuracy reference
   ↓ export
[Layer 2] ONNX      ONNX Runtime loads it and produces boxes  ──→  proves "model + graph" are fine
   ↓ ATC compile
[Layer 3] OM        the board loads it and produces boxes  ──→  proves "conversion" is fine
```

If ONNX is fine but the OM misbehaves, the problem is in the ATC conversion (parameters, TBE
dependencies, soc_version). If ONNX itself misbehaves, do not touch ATC yet.

Three-layer consistency measured on the board (CANN 7.0.RC1, Chestnut Pi 310B):

```
PyTorch baseline  5 objects (bus 0.8729, person ×4)
ONNX              opset 11, images[1,3,640,640] → output0[1,84,8400], 12.85 MB
OM                cosine similarity vs ONNX 0.99999976, per-box IoU ≥ 0.9961
End-to-end perf   36.7 ms / 27.0 FPS (pre-processing 16.0 + inference 15.2 + post-processing 5.3)
Pure inference    15.18 ms / 65.9 FPS
```

## 8. Caveats

- **CANN must be installed on a Linux filesystem** (`/usr/local/Ascend`). Do not install it
  under `/mnt/d/` or similar Windows mounts: NTFS does not support symlinks or the executable
  bit, and the installation will fail.
- **Use ASCII names for directories and files.** The CANN toolchain handles non-ASCII paths
  inconsistently and conversion can fail.
- **Do not run `apt upgrade` casually.** The board's Ubuntu and CANN were validated together;
  upgrading system libraries can break CANN's dependencies. Back up your OM models first.
- Every new terminal needs `source /usr/local/Ascend/ascend-toolkit/set_env.sh`;
  `setup_yolov8_demo.sh` has already written it into `~/.bashrc`.
- During ATC conversion a flood of `ImportWarning` / `SyntaxWarning` messages appears. That is
  normal TBE noise — as long as the run ends with `ATC run success`, you are fine.
- An OM only loads on the **same chip model with a compatible CANN version**. Moving across
  chips (e.g. 310B → 310P) requires re-conversion.
